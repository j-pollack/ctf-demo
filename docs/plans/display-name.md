# Display names on the leaderboard

Worktree: `/Users/jonathan/Code/ctf/.worktrees/display-name`
Branch: `feature/display-name`, created from `feature/screen-actions` at `3dd9ef6` (pull request 37's head).
Authorization: no commit, push, merge or deployment by the developer. No live database or Neon access. Tests use disposable local Postgres and synthetic credentials.

## Request

The user's words:

1. "offer users the ability to have a display name, and tell them this is for the leader board. It's just one input box, allows for word characters, number characters, and -, but no other special characters. We also want to put input validation for that via Jev to check whether this display name is inappropriate / rude."
2. "this should be a mandatory field during sign up."
3. "that means there needs to be a user account page where they can (a) edit their email, and also (b) edit their display name"
4. The account page and the sign-up addition match the site's terminal style.

## Problem

The leaderboard labels each player `Player ` plus six hex digits of a hash of the account id. Players cannot tell who is who, and cannot pick how they appear. Better Auth's `name` column exists but is empty for every member account. Players also have no way to change the email their account signs in with.

## Design

- **Storage.** The name lives in a new user column `displayName`, declared to Better Auth as an additional field with `input: false`, the mechanism `isAdmin` already uses. Better Auth's own `name` column is not used. Any signed-in user can write `name` through `/update-user`, and `/sign-in/magic-link` accepts it in the body, so a name stored there would skip validation and Jev. With `input: false`, Better Auth refuses `displayName` from every client endpoint, and only the app's own route writes it. Guests keep `name = 'Guest'` and are unaffected.
- **Uniqueness.** A unique index on `lower("displayName")`, partial on non-null values. The route checks for a taken name before asking Jev, so a taken name costs nothing. The index decides a race: the loser gets "That name is taken."
- **Validation.** `lib/display-name.ts` trims the input, then requires the pattern `[A-Za-z0-9_\-]{3,24}`, compiled as `^(?:pattern)$` with the `v` flag, which is how a browser compiles an input's `pattern`. An unescaped hyphen in the class is an error under `v`, and a browser then drops the pattern, so the hyphen is escaped. Anything else, including a non-string, is refused with one message naming the rule. The pattern and the rule live in `lib/display-name-rule.ts`, which imports nothing, so the account page's client bundle does not pull in the server's `node:crypto` through `GameError`. The browser input carries the same `pattern`, `minLength` and `maxLength`, but the server check is the one that counts.
- **Jev check.** One request per save, state `{ name }`, question set `display-name-v1` with three Noul questions: offensive (rude, hateful, a slur, an insult, harassment), sexual, and impersonation (staff, admin, moderator, the system or the monitor). The name is refused when any answer is at or above 0.6, set from the measurement under Evidence. Refusal copy: "That name can't be used on the leaderboard. Try another." Every verdict logs one `display_name.checked` event at info level with the user id, the name, the three scores, the threshold and the outcome, so the threshold can be recalibrated from real traffic.
- **Fail closed.** If Jev errors, times out (3 seconds) or returns an unusable answer, nothing is saved and the player sees "We couldn't check that name right now. Try again." If the daily cap refuses the reservation, nothing is sent or saved and the player sees "Name checks are paused until tomorrow (UTC). Try again then." Both are status 503. Names are public, so an unchecked name is never stored.
- **Billing.** `ctf.inference.game_id` becomes nullable and gains `user_id`. A name check reserves a row with role `account`, `game_id` NULL and the user's id, under the same `daily_spend` row lock and daily cap as every other call, and settles through the existing `settleInference`. A check constraint requires either a game, or role `account` with a user. Settlement updates `ctf.games` by `game_id`, which matches no row for an account call, so run budgets and the leaderboard's spend are untouched. A check that never got usage is charged at its input ceiling, the rule the screens use. One check costs about 1,500 input tokens at 0.042 microdollars per token.
- **Rate limit.** At most 20 name checks per account per UTC day, counted from the account's `account` rows under the same lock. Past the limit: "You've checked too many names today. Try again tomorrow." with status 429.
- **Endpoint.** `POST /api/account/display-name` with `{ displayName }`. It checks the request origin, requires a signed-in member through the existing `player()`, and only ever updates the session's own user. There is no user id in the request.
- **Mandatory, and where it is collected.** The name is asked for right after the first verified sign-in, before play. A member without a name who opens `/play` is sent to `/account?next=/play`. A magic link lands on `/play` by default, so a new account arrives there straight after its first sign-in. The account page explains that a name is needed to finish setting up and to start a run, and after a save it loads `next`. A nameless member can still browse the rules, the board and their runs. `POST /api/games` refuses a member without a name with status 403: "Choose a display name on your account page before you start a run." Where the game shows that error, it adds a link to `/account?next=/play`. After a save without `next`, the setup notice goes away at once. The same gate covers new accounts and the three existing nameless accounts.
- **Email change.** Better Auth's change-email flow with both steps. A link goes to the current address first. Opening it sends a verification link to the new address. Opening that one changes the email. The new address is canonicalized like sign-in addresses. Guests and accounts whose email is not verified are refused with 403, because Better Auth skips the current-inbox step for an unverified account. Better Auth answers success without sending mail when the new address already belongs to an account. In Better Auth 1.7.6 it awaits the send for a new address but not for a taken one, so the response time alone would reveal which addresses exist. The sends therefore run as background tasks after the response, through Next's `after()`. A new address, a taken one and a failed send answer with the same status and body at the same speed. `/change-email` is limited to 3 requests per address per 10 minutes. Mail goes through the same Resend sender as magic links. A failed confirmation send is logged with confirmation-link wording, not sign-in wording. If `after()` cannot run during a production request, the unawaited send is logged as `auth.background_task_unawaited`. Because the response now returns before the send, the form clears the address after a send and disables its button while the field holds the address just sent to, so pressing Enter or the button twice cannot send the same change twice. A duplicate confirmation was once seen in a local dev run. That run's server log shows a single change-email request, so the guard does not explain it, and it did not recur in four later sends. Configuring that sender also enables Better Auth's public `/send-verification-email` endpoint, which nothing here needs, so it is added to `disabledPaths`. Each link lands on the account page with its own notice: `?email=confirmed` after the first link, `?email=changed` after the second, and an expired-link notice when Better Auth appends `error`. A signed-out visitor who opens a link keeps `next`, `email` and `error` through sign-in.
- **Leaderboard.** Shows `displayName`. A capture by an account without one still shows the hashed label. The board's query never selects `email`. The board's footnote and the rules page said "Names are anonymous."; both now say "Players appear under the display name they chose."
- **Account page.** `/account`, outside the `(game)` route group because that group's client UI picks its panel from the path. A server component reads the session, sends a signed-out visitor to sign in, and renders two forms under the headings Leaderboard and Email. The site header has one Account menu for signed-in members, with Settings, a link to this page, and Sign out. Signed-out visitors keep Sign in. Signing out on the account page replaces it with the sign-in page, because its content was rendered for the account. On any other page it refreshes the server-rendered parts and moves focus to the Sign in control that replaces the menu.
- **Sign-in page.** One added line tells a new player they will choose a leaderboard name after opening the link.

## Lead decisions the user can overrule

1. ASCII letters, digits, underscore and hyphen, 3 to 24 characters, surrounding whitespace trimmed, no internal spaces. The user's "word characters" is read as ASCII.
2. Names are unique ignoring case, because the board identifies players by them.
3. Jev refuses at 0.6 on any of three questions, and fails closed when unavailable.
4. The name is collected after the first verified sign-in, not on the email form. Reasons: the sign-in and sign-up form is one email box, so asking for a name there would either ask returning players every time or reveal which emails have accounts. A Jev check before the email is verified would let anyone spend the shared daily budget with unverified requests. And a name held for an unverified link would block others from it. One gate also covers the three existing accounts.
5. `displayName` is a new column instead of Better Auth's `name`, because `name` is client-writable.
6. Name checks are billed with a nullable `game_id` and role `account`, under the daily cap, with a per-account daily limit of 20.
7. Email change needs both the current and the new inbox, which stops someone holding only a stolen session from moving the account to their own address.
8. Saving the same name again is a no-op and does not ask Jev. A change of case alone is checked again, because the board shows it differently.
9. The header's Account menu is the ui-sdk Menu, which follows the WAI-ARIA menu button pattern. Click, Enter, Space and ArrowDown open it on the first item. Arrow keys, Home, End and typeahead move between items. Escape returns focus to the button, and an outside click or choosing an item closes it. In that pattern Tab closes the menu and moves on, rather than moving between items. The items stay reachable by arrow keys. A disclosure with tabbable links would need a hand-built widget beside an installed library that already ships this one.

## Out of scope

- Moderating existing names after the fact, or an admin rename tool.
- Running the opt-in live check `npm run smoke:display-name` (`scripts/display-name-smoke.ts`), which sends one ordinary and one rude name to real Jev and asserts their verdicts. It is paid and needs the user's approval.
- Showing display names anywhere other than the leaderboard and the account page.

## Migration wiring

`033-display-name.sql` touches `ctf."user"`, which Better Auth's migrations create, so `scripts/setup.ts` runs it after them, beside `004-rate-limit-timestamp.sql`. The other integration files apply the game migrations before Better Auth's, so 033 cannot join their lists. Better Auth itself adds the `displayName` column there, from the additional field, which is all their run-start tests need. `tests/integration/display-name.test.ts` applies setup's list in setup's order and checks that 033 runs after Better Auth.

## Evidence

The lead ran the `display-name-v1` questions against real Jev on 40 names, saved in `.artifacts/display-name/jev-names.json`. 25 are ordinary handles, including lookalikes such as Scunthorpe, Dickens_fan, kill-9 and assassin_7. 15 should be refused: impersonation, insults, sexual names and a threat. The run used 22,604 input tokens, about $0.001.

| Threshold | Ordinary names refused | Names that should be refused but were allowed |
| --------- | ---------------------- | --------------------------------------------- |
| 0.5       | 2 of 25                | 0 of 15                                       |
| 0.6       | 1 of 25                | 0 of 15                                       |
| 0.7       | 1 of 25                | 1 of 15                                       |

At 0.5 the two refused ordinary names are Dickens_fan, with sexual at 0.54, and AdminOfNothing, with impersonates at 0.85. At 0.6 only AdminOfNothing is refused. The closest name that should be refused is n00b_h8er, with offensive at 0.66, which 0.7 would allow. The threshold is 0.6.
