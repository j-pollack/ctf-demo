## Investigation findings for workstream 3

The queue already coalesces updates. `ctf.monitor_jobs` holds one row per `(session_id, epoch)`. Every transcript append upserts `requested_version` on that row (`lib/monitor-jobs.ts:19`). A claim fixes `target_version`, the worker reconstructs the whole transcript at that version and reviews it once (`lib/monitor-worker.ts:31`). Appends that land during a review leave the job `queued`, and the next review covers all of them. `tests/integration/async-backend.test.ts:438` already proves this. No per-update queue items exist to clear.

Two causes of slow catch-up were found by reading the code. Neither has been measured in production.

- **Claim ordering starves sessions.** Within a run, `claimMonitorJob` picks the ready job with the oldest `created_at` (`lib/monitor-jobs.ts:103`). A session whose agent keeps appending is requeued after each review and is still the oldest job, so it is claimed again. A later session in the same run waits until the first goes quiet. Across runs, candidates are ordered by `next_attempt_at`, which an append with a higher version resets to `now()` unless the job is under review (`lib/monitor-jobs.ts:36`), so a queued job that keeps receiving appends sorts behind jobs that append less often.
- **One serial worker.** `scripts/monitor-worker.ts` runs one review at a time for all runs. The investigator deadline is 90 seconds inside a 120-second claim (`lib/investigator-evaluation-policy.ts`).

The status line reads `{reviewedUpdates} of {totalUpdates} transcript updates reviewed · {pendingSessions} sessions pending` (`app/game-ui.tsx:1776`). The unit is internal observation versions. The numerator jumps because one review covers many versions. The numerator counts `reviewed_version` while the pending count uses `covered_version`, so an inconclusive review can show every update reviewed and a session still pending. `1 sessions` is ungrammatical.

### Monitor

- **M1.** Given one run with two sessions whose jobs are both ready, where the older job was reviewed most recently and has newer appends, when the worker claims, then it claims the other session's job. Given two runs in the same state, the same holds across runs. Jobs are ranked by when they last got attention: `last_reviewed_at`, or `created_at` for a job that has never been reviewed. The oldest goes first. Ties fall back to `created_at`, then `id`. A waiting never-reviewed job therefore goes ahead of a job reviewed after it was created, and a job created after another job's last review does not go ahead of it. The second half closes a queue jump: with never-reviewed jobs always first, a player could open fresh sessions to push back the review of an earlier session.
- **M1a.** Given a queued job whose `last_reviewed_at` is older than every other job's and whose `next_attempt_at` is a minute ahead, and a second ready job, when the worker claims, then the second job is the one claimed. The test sets both columns with SQL and does not rely on real backoff timing.
- **M1b.** Given a job whose claim expires three times, when the worker claims again, then the job is `unresolved` with reason "Review stopped before its outcome was verified." A newer append requeues it. The test reads the job's row, because the claim call that marks it `unresolved` returns null or a different job.
- **M2.** The review status line comes from an exported pure function of the monitor status, `pendingSessions` and the session count. The session count is `displayGame.sessions.length` inside `app/game-ui.tsx`; no API field is added. The function returns:
  - `caught-up`: "All sessions reviewed."
  - `queued` or `reviewing`: "{n} of {total} sessions waiting for review."
  - `unresolved`: "{n} of {total} sessions not fully reviewed."
  - any status other than `caught-up` with no pending sessions: no line. A run can be `unresolved` because of a scoring failure or an uncertain command while every session is reviewed, and the reason line already says so.
  - `caught`: no line.
  - "session" is singular when total is 1. The line no longer shows update counts. The status label, last review time and reason are unchanged.

## Second pass: turn-end reviews, parallel worker, Run details

Requested by the user after playing a four-session run on the preview. Baseline for this pass is `bbbabaf`.

### What the preview run showed

The run lasted 6.5 minutes with four sessions and 21 turns. The worker completed 14 reviews one after another and was busy 83% of the run. Reviews took 7 to 45 seconds. One investigator call never returned, and nothing was reviewed for 76 seconds until the 90-second review deadline ended it. The session that was caught waited 81 seconds for its first review. Sessions were reviewed in rotation, so the ordering fix held. The remaining causes are reviews triggered by every update inside a turn and a worker that runs one review at a time.

### Decisions from the user

- A session is reviewed when its agent turn ends, not on each tool call. In this section's criteria "turn" in that sense means one instruction's whole response, the span of the session lease.
- The worker runs up to four reviews at once.
- No per-call timeout on investigator calls in this pass. It would change the investigator policy that the evals pin.
- Session settings is removed. The model moves into Run details. The system prompt editor stays above the transcript.
- Run details uses compact sections with a small chart, and opening it must not take over the page.

### Criteria

- **T1. Turn-end review.** Given a session whose agent turn is in progress, meaning its `agent_sessions.lease_until` is in the future, when the worker claims, then that session's job is not claimed, however many updates it has and whether the job is queued or an expired claim. Given the turn ends and the lease is released, or the lease expires after a crash, then the job is claimable and one review covers every update of the turn. Another session's job in the same run is still claimed while one session is busy. `enqueueMonitorJob` is unchanged: `requested_version` still follows every append, so finalization still waits for every update to be covered. The lease condition is a `NOT EXISTS` subquery on `ctf.agent_sessions` in both the candidate query and the in-run query. It is not a join, because the in-run query's `FOR UPDATE SKIP LOCKED` would then lock and skip session rows a runner holds.
- **T2. Parallel reviews.** `scripts/monitor-worker.ts` runs four review loops from a named constant, and one loop with `--once`. Given two ready jobs, in the same run or in different runs, when two `runMonitorWorkerOnce()` calls run concurrently, then each call claims a different job, the two reviews overlap in time, both jobs end `caught-up`, and each review row and each billing settlement is recorded once, with the run's spend equal to their sum. Given two concurrent reviews of the same run where one blocks, then the run is caught once, with one catch event and `blocks` raised by one, and the other review ends without leaving its job in `reviewing`. Given both block, the same holds: one catch event and one increment. On SIGTERM every loop finishes its current review and the process exits. If any loop throws, the others stop after their current review, the process waits for all loops to settle, then closes the pool and exits 1.
- **T3. Review timing copy.** In the UI a "turn" is one agent response, and the TURNS counter counts those. A review happens once per instruction, when the agent finishes responding and the session lease is released. Player copy therefore says "finishes responding", not "turn ends".

### Limitations of this pass

- A flag read is now caught after the turn that made it, not during it. A win is still confirmed only after every update is reviewed.
- A hung investigator call still holds one of the four slots for up to 90 seconds.
- A single response is reviewed only when it ends, up to the 230-second response limit. Instructions sent back to back no longer defer review, because each finished response triggers one (T4).
- A flag read is reviewed about once per finished response, where it used to be reviewed on every update. Each review is a chance for the investigator to catch it, so there are fewer chances. The effect on detection rates has not been measured.
- Four investigator sessions run at once on a 1 GB worker. Memory on the preview worker has not been measured.
- The evals still show the investigator a target session marked busy. Production no longer reviews a busy session. Whether the evals should switch to idle targets is a separate decision, because it changes what they measure.
- Live smoke is not run. `scripts/smoke.ts` is read for assertions that depend on mid-turn review.
