## Problem

Automatic production domain assignment has been off since 2026-11-27 23:11 UTC, so the `promote web` job is the only thing that moves the domain. In its first release that way, run `46084688527` for `1f95535`:

- the lookup found the staged deployment and decided `promote`;
- the eight read-only checks on the deployment's own URL passed;
- `npx vercel@67.0.0 promote` failed with "Not able to load user because of unexpected error: User not found. (404)";
- the step's fallback read the domain, which still served the previous deployment, so the step failed;
- the rollback step ran the CLI, which failed the same way, and then confirmed the domain served the previous deployment.

Production stayed on the previous release and stayed healthy. The lead finished the release by hand with a logged-in CLI at 23:53:49 UTC. Until this is fixed, every release stops before promotion.

The token in `VERCEL_TOKEN` works for every REST read the job makes. The CLI needs to load a user before it does anything, and this token cannot. The job should not depend on which kind of token the CLI accepts, and it already has a tested REST client.

## Facts established

By the lead, on the live project:

- `POST /v10/projects/<project id>/promote/<deployment id>?teamId=<team>`, called for the deployment that already served, answered 409 "already the current production deployment" and changed nothing.
- An ordinary promote leaves automatic assignment off: it read `false` after the hand promote of `1f95535`. A promote after a rollback turned it back on in the drill on 2026-11-27. A rollback sets it to `false`.

By the plan verifier, from the source of `vercel@67.0.0`, Vercel's OpenAPI document and its documentation:

- **Why the CLI failed.** Every promote and rollback first reads `GET /v2/user`. A token scoped to a team or a project is refused there with a 404, with or without `--scope`. Such a token can read and write the resources in its scope, so nothing suggests it cannot promote. The role of the person who created it decides that.
- **Promote** is `POST /v10/projects/{projectId}/promote/{deploymentId}` with `teamId`, content type JSON and body `{}`. It answers 201, or 202 when it is queued behind a rolling release, and returns before the move finishes.
- **Rollback**, as the CLI sends it and as the drill ran it, is `POST /v9/projects/{projectId}/rollback/{deploymentId}` with the same shape.
- **The move is a background job.** `GET /v9/projects/{id}?rollbackInfo=true` shows it in `lastAliasRequest`: `toDeploymentId`, `type`, and a `jobStatus` of `pending`, `in-progress`, `succeeded`, `failed` or `skipped`. Without `rollbackInfo=true` that field is null. A project runs one such job at a time and answers a second request with 409.
- **The setting** is `autoAssignCustomDomains` on the same record, and `PATCH /v9/projects/{id}` accepts it.

## Scope

1. **`scripts/release-deployment.ts`**: three commands replace `verify`.
   - **`promote <deployment id>`** sends one `POST` to the promote path, then polls the production domain's alias every 3 seconds for at most 2 minutes until it serves that deployment. It passes only when the alias serves it.
     - A 409, a 429, a 5xx or no answer is followed by the poll, because the domain may already serve the deployment or may still move. A 202 fails at once. Its message names a rolling release, which this project does not use, and says Vercel has queued the promotion and may still perform it later without this job's checks. Any other status fails after one read of the alias.
     - The `POST` is sent once and never repeated.
   - **`rollback <deployment id>`** reads the alias first. When it already serves that deployment, it sends nothing and says that nothing had moved. Otherwise it sends one `POST` to the rollback path and polls by the same rules.
   - **`assignment-off <deployment id>`** runs after a promotion. It polls the project record with `rollbackInfo=true` for at most 1 minute until `lastAliasRequest` names that deployment with a final status, reads `autoAssignCustomDomains`, sends `PATCH` with `{"autoAssignCustomDomains":false}` whatever it read, and reads the record again. It passes when the job was final and the last read is `false`. It writes a warning when the first read was `true`. When the job is not final within the minute it still sends the `PATCH`, and then fails: the setting could still turn on when the job ends, and the message says to read it by hand. The `PATCH` is tried at most three times, again only after a 429, a 5xx or no answer. Each request in this command has a 15 second timeout, so its worst case stays under 3 minutes.
   - Every command prints `serving_id=<id>` when it has read the alias, and `rollback` prints `moved=true` or `moved=false`. Failure messages name the request's status and the serving deployment. The token is never printed.
   - Every request carries the bearer token and `teamId`. A `POST` carries the JSON content type and the body `{}`. The project id, the team id and the deployment id are checked against the id pattern before they reach a URL.
   - The polls sleep and read time through the injected clock and read the alias directly, without the two second retry of the existing serving read, so a test runs them in no real time. Worst case for `promote`: 30 seconds for the request, 2 minutes of polling and 30 seconds for a last read, 3 minutes against the step's 4.
2. **`lookup`.** When the decision is `already-serving`, it reads the setting. With the setting `true` it fails: the message says automatic assignment is on, that the live site was not checked by this run, and how to turn the setting off before re-running. With it `false` it keeps today's warning, which covers a re-run and a release finished by hand. When the setting cannot be read it fails.
3. **`.github/workflows/migrate-prod.yml`.**
   - The promote step runs `promote "$NEW_ID"`.
   - The separate verify step goes: `promote` passes only when the domain serves the deployment.
   - A new step after the live checks runs `assignment-off "$NEW_ID"` with the condition `steps.decide.outputs.decision == 'promote'`, so it runs only when this job promoted and everything before it succeeded, and has a 3 minute timeout. It is not part of the rollback condition: a release that is live and passed its checks is never rolled back because a setting could not be read or set. Its failure fails the job with an error that says the domain moved.
   - The rollback step runs `rollback "$PREVIOUS_ID"`, reads `moved` and `serving_id`, and says either that it rolled back or that nothing had moved. Its condition becomes `always() && steps.promote.outcome != 'skipped' && !(steps.promote.outcome == 'success' && steps.live.outcome == 'success')`.
   - `VERCEL_CLI` and both `npx` calls go. The token reaches only the steps that call Vercel. The step timeouts add up to 25 of the job's 30 minutes: the verify step's 2 go, the setting step's 3 come, and the rollback step has 5 because its first read can retry.
4. **`deploy/operations.md`.** The release order and the section on finishing, repeating or undoing a release describe the API calls and the setting step. They say that after any promote by hand the setting is read and turned off, and how.
5. **`docs/plans/release-promotion.md`.** Its rollout record gains the failed first promotion and points here.

## Risks and open questions

- **Whether the token may promote and change the setting.** Its scope allows writes. The role of its creator decides. A refused promote fails fast with a 401 or 403 and production stays where it is. A refused setting change fails the job after a good promotion and does not roll it back. The lead asks the user which scope and role the token has.
- **A window after a promote that follows a rollback.** The setting is `true` from that promote until the setting step turns it off, a few seconds later. A newer production build that became ready inside that window would be assigned by Vercel without this job. Accepted.
- **The rollback path is the CLI's.** Vercel's public reference documents `/v1/projects/{projectId}/rollback/{deploymentId}`. The `/v9` path is what the CLI sends and what the drill ran. If Vercel removes it, the documented path is the fallback.
- **One host is judged.** The job reads the alias of the production origin. A job that Vercel marks failed can leave another production domain behind.
- **A rollback during a pending promote.** A rollback sent while Vercel's job for a promote is still pending answers 409 and is not sent again, so a promote that was cancelled mid-job can still land. The step then ends saying the site needs attention.
- **A promotion that Vercel performs slowly.** The poll allows 2 minutes. The hand promotes took 2 to 3 seconds.
- **Releases stop before promotion until this merges.** The lead finishes any release in between by hand, as `deploy/operations.md` describes.

## Plan verification

An independent read-only check on 2026-11-27 approved with changes, all folded in. A second pass the same day confirmed each closed and added five small edits, also folded in: the setting step fails when Vercel's job never becomes final, it runs only when this job promoted, its retries and timeout are bounded, its tests assert `rollbackInfo=true` and the request's shape, and the 202 message says the promotion may still happen.

- With the setting check inside `promote`, a failed read or change would have failed the promote step, and the rollback condition would then have undone a release that was live and had passed its checks. The setting is now its own command and step after the live checks, outside the rollback condition.
- The setting is read only after Vercel's job for the promotion is final, because the alias can move before the job ends, and it is turned off on every promotion, which also proves the token's right to do so on every release.
- A rollback first reads the domain and sends nothing when the target already serves, so a failed promotion that moved nothing does not produce a rollback request with an undocumented answer.
- The separate verify step and command go. The polls use the injected clock. The requests carry what the CLI sends. A 202 fails at once. The rollback path is the CLI's, which the drill already ran, so no second hand exercise is needed.
- The verifier found why the CLI failed: it reads the user record first, and a token scoped to a team or a project is refused there.
