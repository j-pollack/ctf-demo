## Scope

Three browser stories that need no Sprite and no monitor worker, and the harness changes they require.

1. A member changes their email on `/account`.
2. An admin switches the game-rule toggles on `/admin`, and visitors see the changed rules.
3. A visitor's contact message reaches the admin mailbox, and an admin replies to it by mail from the panel.

## Non-goals

- A reply from the visitor arriving in the thread. The Fastmail fake lives in the server process and a browser test has no way to seed inbound mail. `tests/integration/feedback-mail-thread.test.ts` covers it. A control channel into the fake is not added.
- Email-change refusals: a guest, an unverified account, a taken address, a failed send and the rate limit. `tests/integration/display-name.test.ts` covers them.
- The effect of a game-rule toggle on a run. That needs a run and belongs to the run stage.
- Failure paths of the faked services, for the reason given in the stage 2a contract.
- Changes under `app/`, `lib/`, `db/` and `tests/integration/`. If a story cannot be driven without one, the developer stops and returns to the lead.

## Facts from the survey of the code

- **Email change.** `authClient.changeEmail` posts to `/api/auth/change-email`. Mail 1 goes to the old address with subject "Confirm your Capture the flag email change". Opening its link redirects to `/account?email=confirmed` and changes nothing. Mail 2 goes to the new address with subject "Verify your new Capture the flag email". Opening its link sets `ctf."user".email` and redirects to `/account?email=changed`. Both mails are sent after the response, through Resend, which the suite already fakes. The limit is three requests per ten minutes per client address.
- **Game rules.** Each rule on `/admin` is a form whose submit button has `role="switch"` and the rule's label. The action upserts `ctf.settings` with `on` or `off` and redirects to `/admin`. A failure shows nothing on the page and logs `game_rule_change_failed`. The pages `/`, `/rules` and `/play` read the stored rules on each request and change their copy.
- **Feedback mail.** `mailConfig()` needs `FASTMAIL_API_TOKEN` and `CONTACT_EMAIL`. With both set, a contact message sends a notification to `CONTACT_EMAIL` after the response and stores `mail_thread_id`. The thread page reads the thread from Fastmail, and a reply is sent through Fastmail and never stored in Postgres. `createFastmailFake` in `tests/integration/fastmail-fake.ts` answers exactly `https://api.fastmail.com/jmap/session` and `https://api.fastmail.com/jmap/api/`, validates each request and keeps the mail in memory. It refuses a Message-ID over 64 characters as a not-created result, which the app logs and does not throw.
- **Two gaps in the stage 2a harness.** `signInLink` returns the newest mail to an address, whatever its subject. The end-of-run log check matches only `route.failed` and events ending in `_read_failed`, so `feedback_mail.notify_failed` and `game_rule_change_failed` would pass unseen.

## Design

1. **Mail by subject.** The stack module reads a mail for a given recipient and subject and waits for it. The sign-in helper uses it with the sign-in subject.
2. **Several fakes behind one guard.** `guardedFetch` takes a map from exact URL to the fake that answers it. The preload builds it from `createAccountFake` and `createFastmailFake`. A URL outside the map and outside loopback is refused and recorded as before.
3. **Mail sent through Fastmail is recorded.** After each Fastmail request, the preload appends each new submission to the mail file as one JSON line. The line holds the recipient and the reply-to address as plain strings, the subject, the text, the mail's own message id, the id it replies to and its references. The tests read these lines as they read sign-in mail.
4. **Environment.** The server gets a synthetic `FASTMAIL_API_TOKEN` and `CONTACT_EMAIL=contact@ctf.example.test`. Only the server stage sets them. The build and the migration keep both empty, and the test stage gets `CONTACT_EMAIL` for its assertions.
5. **Server failures fail the story that caused them.** The stack module returns the server log's failure events since the last take. A failure event is a JSON log line whose `event` ends in `failed`, or the event `auth.background_task_unawaited`, which the app logs when it cannot schedule a task after the response and runs it without waiting. The cursor is a byte offset kept in a file in the artifacts directory. It advances only to the last newline, so a half-written line is never consumed. The runner creates the cursor file and passes the log path and the cursor path in the test environment, and its offline test covers both. Each journey ends by asserting that the list equals the events it declared as expected, which is none by default. A failing journey also takes its events, as it does for violations, so the next journey starts clean. The runner's end-of-run check covers the lines after the last cursor with the same rule. The function that picks failure events from log lines has one definition, in `scripts/test-e2e.ts`, and an offline test.
6. **Stories.** One journey file per story under `tests/e2e/`. They import only the stack module and the browser helper. Settings changed by a journey are restored in `finally`, as the limit journey does.

## Risks and open questions

- **One fake for the server's lifetime.** The thread a reply joins exists only in the Fastmail fake's memory. The preload installs one guard per thread, and stage 2a's runs showed a single evaluation on the main thread. If a request were served by another instance of the fake, the thread page would show only the stored message with no note, and the reply would be sent with no id to reply to and would replace the stored thread id. A5's assertion on the replied-to id detects this.
- **Other failure events.** Widening the log check may surface an event that an existing journey already causes. The developer reports each one to the lead before declaring it expected.
- **The email-change limit.** Three requests per ten minutes per address. The journey sends one from its own address.
- **Opening the second link.** It is opened in the member's own context. In a context with no session it would sign that context in, which the journey does not assert.
- **Global settings.** The game-rule journeys change settings every later journey reads. They restore them in `finally`, and the member-pages journey's heading check accepts both forms.
