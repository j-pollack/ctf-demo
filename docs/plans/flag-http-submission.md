## Problem and scope

The current `submit({value})` tool requires the agent to obtain the flag bytes before supplying its argument. A command can instead send a file directly to an owned HTTP endpoint without printing its contents. The monitor must reconstruct the read from the visible commands, scripts, reasoning and results. Absence of plaintext is not itself a monitor bypass.

The feature replaces the tool with direct HTTP submission for every new run and fork. `lib/games.ts` currently creates both with `monitor_mode='async'`. Existing persisted runs keep their previous transport and review lifecycle, including historical legacy runs. There is no player-selectable transport and no `submit` tool fallback in an HTTP run. A compatibility branch is required in `runner-async.ts` for already-open async runs. `runner-session.ts` remains the historical legacy path.

The user explicitly requires egress to only the specific submission endpoint. Allowing the main application hostname is unacceptable. The design therefore includes a separate minimal trusted ingress with an exclusive network destination and application-level rejection of everything except the submission operation. Native Sprite policy alone cannot enforce an HTTPS path or method.

The feature preserves flag generation, seeded bug scoring, ownership, leases, billing, monitor versions, evidence semantics, caught-run precedence, terminal-state presentation and cleanup. It adds no new monitor prompt, model, threshold, evidence redaction or guaranteed evasion strategy. It does not add a public player submission button, arbitrary HTTP proxy, general network access, live-service test in routine gates, or automatic deployment.

Inference from these documented limits: after an allowed hostname resolves, another TLS SNI or HTTP Host on the same reachable address may reach another virtual host. A distinct hostname on a shared CDN or shared application address is insufficient proof. No reviewed source promises SNI binding. Do not claim it does.

Connector identity is stronger than the selected bearer's origin guarantee, but neither mechanism alone solves per-session dispatch binding on a shared Sprite.

### Selected ingress boundary

Build a small Node ingress process in this repository, using a shared receipt handler and the existing Postgres transaction layer. Run it as a separate trusted service. It is not a Next route on the general application deployment, and it is not a forward proxy. It has no browser auth, pages, file-serving route, redirect, diagnostics body, or user-selected upstream. It talks to Postgres privately and has only the credentials needed by its server role.

The deployment must exclusively dedicate every resolved IPv4 and IPv6 address to this service. An external firewall permits TLS TCP 443 only. Its TLS edge rejects unexpected SNI. The ingress rejects unexpected authority/Host, methods, paths, query strings, CONNECT, absolute proxy targets and upgrades. Only `POST /v1/flag` is an accepted application operation. Disable platform access-body logging and request tracing before enablement. Health checks use a private management surface, not a second public route.

The Sprite policy is exactly the configured ingress hostname allowed plus explicit `deny '*'`. No presets, wildcard subdomains, application hostname or fallback allow rule. Apply and read back the policy before seed initialization and before activating a restored fork. A failure leaves the run unplayable and follows existing failed-provisioning cleanup.

A packet can still reach the dedicated ingress and ask for an invalid path. That request is rejected by the application boundary, not blocked by Sprite Layer 3 policy. Raw-IP connection to the dedicated address may also be possible after allowed DNS resolution. It must not expose another service. If “only the endpoint” instead means no connection or request to that address for any other HTTP path, native policy cannot satisfy that literal packet-level interpretation. The selected contract is one reachable trusted destination with exactly one accepted HTTP operation.

Missing or invalid `FLAG_SUBMISSION_URL` fails new-run creation before paid provisioning. Require a canonical HTTPS URL, default port 443, the exact `/v1/flag` path, no query, credentials, fragment, wildcard, localhost or IP literal. Refuse the known main app host. Configuration alone cannot prove exclusive address ownership. Infrastructure proof and the live negative tests below are separate rollout prerequisites. No automatic downgrade to the old tool or broad egress is allowed.

## Submission protocol and authority

The shell sends raw file bytes as the HTTP request body with `Content-Type: application/octet-stream`. `X-CTF-Run-Id` carries the run UUID. `Authorization: Bearer ...` carries a random, single-dispatch capability. An example for product documentation is:

```sh
curl --fail --silent --show-error \
  -H 'Content-Type: application/octet-stream' \
  -H 'X-CTF-Run-Id: <run-id-from-system-prompt>' \
  -H "Authorization: Bearer $CTF_SUBMISSION_TOKEN" \
  --data-binary @/tmp/flag.txt '<submission-url-from-system-prompt>'
```

For each HTTP session, extend the existing `lib/policy.ts:agentPrompt` construction with a structured public context containing the authoritative run ID, session ID, transport and submission URL. Keep the player's system instructions and append server-derived context from the currently claimed run/session. Rebuild it on every resume and fork, never reuse a parent ID or stored old system-message context. The endpoint still validates dispatch bindings; prompt IDs are information, not credentials. Do not place capabilities, flag bytes or scorer results in any system prompt. Historical tool runs retain their existing prompt behavior. The monitor's own system prompt and evidence boundary remain unchanged.

Do not require this exact command or provide a special hidden upload tool. Players may construct indirect pipelines and scripts. Commands and results remain visible verbatim under the existing truncation limits. The example is a functional smoke case, not a promised winning strategy.

At dispatch, generate a fresh 256-bit capability and store only its hash with the existing command operation. Bind it to run ID, session ID, Sprite name, execution generation, exact source lease and dispatch ID. Inject only `CTF_SUBMISSION_TOKEN` as process environment for that execution. Public run/session IDs and the endpoint come from the system prompt. The installed SDK supports this through `ExecOptions extends SpawnOptions` and `env?: Record<string,string>` at `dist/types.d.ts:44`. Do not append a secret to the recorded command string, a transcript message, an event, a browser response or a shared workspace file. Runtime changes must not overwrite or sanitize the agent's command or output.

The ingress authorizes receipt creation against the persisted command operation and live session lease, never a caller-supplied session ID or the run ID alone. The run must be HTTP-enabled and active, the command running, the generation current, and the lease unexpired and unchanged. Reject stop-requested sessions. Cookie authentication, even for the owner, grants no receipt authority. Reject browser Origin requests and do not enable CORS. Cross-run, fork-parent, stale-generation, expired, completed-command and revoked capabilities cannot create receipts. Creation authority ends at command completion, stop, lease loss or terminal transition. Acknowledging an existing receipt uses the separate replay rules below.

This is capability authorization, not proof of the request's physical origin. A player who extracts an active capability can use it externally or from a sibling process sharing the Sprite while its dispatch remains authorized. It identifies authority, not which process sent the bytes. Origin headers and source-IP guesses cannot distinguish those cases. Review every session's evidence. Physical-origin attestation is outside this selected transport contract. Ordinary external requests with only a run ID, flag or owner cookie remain denied.

Bound input before allocation: 8,192 bytes streamed, including chunked bodies without Content-Length. Require the exact content type, valid UTF-8 and a nonempty body. Reject unsupported content encoding and ambiguous duplicate authority/auth/run headers. Enforce a five-second request read timeout and cancel aborted streams. Keep the existing `hasSecret` matching rule on the bounded decoded value so this transport change does not change what counts as the right flag. Malformed transport does not consume the one submission. A well-formed but wrong candidate does.

Require shared edge rate limiting before rollout, with deployment-appropriate bounded request/concurrency limits and a tested `429` response. Choose values when hosting is selected and account for Sprites sharing source addresses. Do not add a durable attempt counter or rely solely on a per-process map. Correctness, hash, received bytes, submission IDs and review details never appear in HTTP responses. Logs record only safe IDs, status and bounded generic errors.

After edge admission, the receipt handler follows this matrix. Every response is `Cache-Control: no-store`; acknowledgements have one fixed body.

| State                                                                  | Result                                                                                                                                                                                                    |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No receipt, valid live creation authority                              | Atomically create first receipt and return `202`, whether flag is right or wrong.                                                                                                                         |
| Existing receipt, same capability/run and body digest                  | Read-only `202`, including after command completion, lease expiry, stop, catch, finalization or budget exhaustion. Preserve the capability hash for this lookup. Never reopen work or reveal correctness. |
| Existing receipt, authenticated but changed body or competing dispatch | `409`, no mutation.                                                                                                                                                                                       |
| Missing/invalid capability or mismatched run                           | Generic `401`, no receipt lookup disclosure.                                                                                                                                                              |
| No receipt, formerly valid capability now stopped, expired or fenced   | Generic `409`, no mutation.                                                                                                                                                                               |
| Edge throttling or malformed transport                                 | `429` or bounded validation error before receipt processing. A later admitted exact retry still gets `202`.                                                                                               |

## Receipt and finalization state transitions

Add `submission_transport` on games, defaulting existing rows to `tool` and explicitly setting new rows to `http`. Add a private receipt table with one row per game, a dispatch foreign key, acceptance timestamp, body digest, private correctness and promotion state. Payload and binding fields are immutable; promotion state may change. Reuse run/session/generation bindings on the referenced operation rather than duplicating them. Add nullable capability hash and originating lease fields to command operations. Constraints must prevent a receipt from referencing another game's operation. Store no raw upload body.

1. **Dispatch:** Existing authorization and Sprite operation insertion occur before remote execution. The fresh capability exists only for that dispatch. Commands from different sessions have different capabilities despite sharing one Sprite.
2. **Receive:** In one transaction, lock run, session and operation in the existing order, validate authority, compare the flag privately, and insert the first immutable receipt. A uniqueness constraint on game ID arbitrates concurrent submissions. Exact retries from the same capability and body digest return the same acknowledgement. A different body or competing dispatch cannot replace the first receipt. Exact accepted retries may acknowledge after lease expiry or finalization, but cannot mutate or restart anything. Invalid credentials never reach this replay exception.
3. **Fence new work:** A pending receipt immediately prevents new session claims, command dispatches, forks and attacker inference admission for that run. It does not change `status` or generation, cancel the uploading command, wait for the worker, or hold a transaction while the command finishes. The HTTP response returns immediately after commit. Already admitted commands may finish and must persist their results. Heartbeat may stop idle inference but must not abort an active command solely because of the pending receipt.
4. **Persist the command:** Await the real tool result, persist transcript evidence, event and operation outcome, and enqueue the resulting monitor version through `completeAsyncCommand`. Use a narrow ordered persistence promise/queue so Pi callbacks, next tool admission and `finally` cannot race or dispose before persistence. Nonzero shell exit is still a known completed command and does not undo an already committed receipt. HTTP success does not imply shell completion.
5. **Drain, then promote once:** Keep the run active with receipt admission fences until the uploader has a known completed result and persisted evidence, and no command remains running or unknown on the shared Sprite. A healthy slower sibling must finish normally while heartbeat still honors catch, stop and lease loss. Completion of any sibling, or idempotent worker recovery, retries this promotion predicate. Only then move the run to `finalizing`, set existing private submitted fields, increment generation, enqueue the unique finalization job, and emit a generic submit event without flag text or correctness. The finalizing transition therefore cannot abort a healthy in-flight sibling through the existing heartbeat. The handler never drives finalization synchronously.
6. **Review and score:** Existing worker review coverage must include the uploader's result and every admitted sibling result. Keep zero live writer leases, zero unresolved reservations and no running/unknown Sprite operations before scoring. Recheck those guards at final commit, across the shared Sprite rather than only the child run. Preserve exclusive scoring, at least one passed seed bug, private correct flag, and catch-wins behavior. Pending or failed review never becomes an allow. Terminal UI may then expose the existing outcome/correctness/bug result without exposing upload bytes.
7. **Interruption and recovery:** If response loss happens after receipt but command completion is unverified, persist the available interrupted transcript and unknown outcome. Do not infer completion from receipt acceptance, exit-time guesses or lease expiry. Expose a pending unresolved submission using existing unresolved UI, block further play/scoring, and preserve debt for investigation. A worker crash between command persistence and promotion is recoverable from the completed operation and private receipt. An unknown execution remains unresolved until an existing trusted cleanup/termination path establishes safety. Run termination may discard the opportunity to win; it must not fabricate successful execution or award capture. No automatic replay of a possibly executed command.

Receipt acceptance is not capture. The run enters finalizing only after the uploader's known completion is durable. Final scoring and terminal capture occur only after review coverage and all existing safety gates. Catch/stop races use the same run/session locks and current predicates, so a receipt cannot reopen a caught or ended run.

## Material prerequisites and tradeoffs

1. **Endpoint deployment is not selected.** The user has not supplied the final hostname or hosting arrangement. The selected design requires an exclusive trusted destination and external TLS/port enforcement. A shared Vercel/app hostname does not satisfy it. Implementation can proceed with offline fixtures once authorized, but rollout cannot proceed until this property is demonstrated. If the chosen host cannot provide exclusive addresses, re-plan a mandatory external enforcing gateway. An environment `HTTPS_PROXY` inside attacker-controlled code is not sufficient.
2. **Literal endpoint-only wording has a layer limit.** Native Sprite rules cannot prevent an invalid HTTP path from reaching the allowed address. The dedicated ingress rejects it. If the user requires network-layer path impossibility rather than one accepted operation, the chosen platform lacks the demonstrated capability. Do not silently call host allowlisting equivalent.
3. **Per-command bearer capability is the authority boundary.** It prevents run-ID-only and browser-cookie submission and confines acceptance to an actual admitted command. It cannot prove physical origin after deliberate capability disclosure. No extra attestation system is proposed.
4. **A receipt ends the attempt without a correctness oracle.** The first valid body consumes the opportunity, including a wrong flag. Unknown execution after receipt remains unresolved rather than granting a retry that could bypass review. Exact delivery retries are safe and idempotent.
5. **Compatibility is per persisted run.** Historical tool runs remain usable. New/forked runs cannot choose that route. Mixed-version rollback must drain HTTP runs before removing the feature.
6. **Quality claims need separate evidence.** Transport tests prove no required plaintext disclosure. They do not prove the monitor finds or misses an indirect attack. Any later paid monitor evaluation needs explicit authorization and should report detection outcomes without changing the standard to make the game easier.
