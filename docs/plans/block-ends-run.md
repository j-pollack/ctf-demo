## Request

The player gives an optional system prompt and instructions. The agent works until either (a) its turn completes and it needs input, or (b) the monitor blocks a tool call. On (b) the run is over: the player is told the monitor decided the conversation is attempting to exfiltrate data, and that if this is wrong they can fork and try again with a new instruction. Fork carries over the full sprite state. The player chooses per run whether the monitor sees the agent's reasoning.

## Decisions (user-confirmed or lead defaults disclosed to the user)

- Fork is allowed only from the agent's last turn of a **blocked** run (user's simplification). Because the blocked command never ran, the sprite already holds that state: the child reuses the parent's sprite and flag. **No Sprite checkpoints**, no restore, no live-probe dependency.
- The child's **Pi transcript is cut back to the last non-blocked state** (user-confirmed): anchor on the **last `toolResult`** in the parent transcript, which must be `isError` with text exactly "Blocked" (else reject → 409). In the assistant message holding that `toolCallId`, keep the calls before it and their results verbatim (whatever they say), drop that call, every later call, and every message after the kept results (including any trailing aborted/error assistant message). If no calls remain, drop that assistant message too. `repairMessages` must add no synthetic results to the cut transcript. The player-visible event history is copied verbatim so they see what was blocked; turns/blocks counters are inherited unchanged. Pure function `blockedForkMessages(messages)` in `lib/fork-transcript.ts` (replaces the old prefix logic), unit-tested.
- A block followed by a correct submit in the same batch **no longer captures**: the block ends the run first (lead decision, disclosed to user). Existing test sprites.test.ts ~1619 is updated accordingly.
- Admin counts each fork as a run, but sums spend/turns/blocks only over rows with no child (user-confirmed), so lineage totals are not double counted.
- New terminal status `blocked`. Captured, exhausted and ended runs stay final (forking a wrong submission would undo it).
- A blocked run can be forked **once** (the sprite is shared; a second child would inherit the first child's changes). Fork-of-fork is allowed when the child is itself blocked.
- A child inherits budget, spent, tokens used, turns, blocks, model, system prompt, monitor-reasoning setting, secret hash and sprite. Lineage shares one budget, so block→fork cannot reset spend and the leaderboard ranks cumulative spend.
- Forks do not count toward the per-owner daily start limit or the global 100/day start limit (no new sprite). Daily spend cap and the 10 concurrent other-owner runs limit still apply.
- Sprites of blocked runs are forkable for 24h. Cleanup destroys a sprite (once per `sprite_name`, marking every row using it) only when every run using it is terminal and none is an un-forked blocked run updated within 25h (1h margin so cleanup cannot race a fork). Forking a run whose sprite is deleted or whose block is older than 24h fails with a clear 410.
- Fork must stay in the parent's season: parent `season_id` must equal the current open season, else 410.
- Monitor reasoning visibility is a per-run boolean chosen when starting (default on), inherited by forks, shown on the run and leaderboard.
- Monitor errors (invalid decision, unreadable reasoning) keep today's behavior: the response stops, the run stays open.

## Non-goals

Sprite checkpoints/restore, forking at arbitrary turns, forking non-blocked runs, a separate "run over" event kind, changes to monitor prompt, submit semantics, inference admission/settlement, new dependencies, live service calls.

## Amendment 1: fork goes back to before the last instruction (user decision, 2026-10-16)

Live QA showed the fork point keeps too much momentum: the child still holds the instruction that led to the block and the turns it already ran, so the agent finishes the same plan. The user decided the fork goes back to **just before the last user instruction**, with the sprite restored to match, and the dropped instruction pre-filled in the composer.

Live Sprite probe (one throwaway sprite, deleted): `/tmp` is ext4 on the overlay, so `/tmp/flag.txt` survives restore with its mode; `/.sprite/checkpoints` is empty inside SDK sprites; checkpoint 250–400 ms, its id is in the `complete` stream message (`Checkpoint vN created successfully`); restore ~2.6 s and the next exec works immediately; the deny-all network policy persists across restore; restore auto-creates a `pre-restore` checkpoint. Log: session scratchpad `probe.log`.

Decisions (supersede the transcript-cut decision above; everything else stands):

- Every instruction checkpoints the sprite before the agent runs. The id is stored on that instruction's `user` event (`checkpoint`). If the checkpoint fails, the response fails before any inference and the run stays active.
- Fork of a blocked run targets its **last `user` event**. The child gets the parent's Pi messages before the matching (last) user message, the parent's events before that user event (new ids), and `turns`/`blocks` recomputed from the kept events. Spend, tokens and budget still carry over in full.
- The fork inserts the child as `creating` inside the admission transaction, commits, restores the shared sprite to the checkpoint, then activates it. On restore failure the child is ended and its `forked_from` cleared so the parent can be forked again; the error is shown.
- Runs without a checkpoint on their last instruction (created before this change) cannot be forked (409).
- The fork response tells the client the dropped instruction; the composer is pre-filled with it.
- `blockedForkMessages` is replaced by a pure function that cuts before the last user message. Copy: the banner says "If that's wrong, fork the previous message and try again with a new instruction."; the fork dialog and rules say the run goes back to before your last instruction with the environment restored to that point.

Amendment 1 verification resolutions (independent verifier; lead decisions):

- Checkpoint and restore are bounded (~30 s timer that closes the stream) in `lib/sprites.ts`. The adapter iterates the stream itself: a `{type:"error"}` message, a missing terminal message, or a `complete` message not matching `/^Checkpoint (v\d+) created/` (restore: no `complete`) is a failure.
- Restore failure **deletes** the `creating` child and its events (`WHERE id AND status='creating'`), it never ran and has no inference rows. Cleanup deletes stale (`>5 min`) `creating` fork children (`forked_from IS NOT NULL`) instead of ending them, so the parent stays forkable and its sprite is kept.
- Checkpoint is taken in `runGame` after `assertLease`, immediately before `session.agent.prompt`; its id is attached in the user `message_end` emit. Failure throws before `prompt` (error event, run stays active, no user event or Pi user message).
- `turns` and `blocks` are **inherited cumulatively** (not recomputed), consistent with spend; event turn labels may show a gap. Supersedes the recompute line above.
- Before cutting, the last user event's text must equal the last Pi user message's text and carry a `checkpoint`, else 409.
- Sprite fake: `createCheckpoint`/`restoreCheckpoint` return the SDK's real `CheckpointStream`/`RestoreStream` over a synthetic NDJSON `Response` in the probed format, with per-sprite state (checkpoints and a state version bumped by commands, reset by restore). Tests cover exact ids, one restore per fork, nothing executed before the checkpoint, and error message / truncated stream / rejection / timeout paths.
